# TrumanWorld 比赛与面试介绍稿

这份文档用于 AI 比赛路演、项目面试、作品集讲解和答辩。核心表达原则是：

- 先讲清楚项目解决什么问题
- 再讲实现方案为什么成立
- 最后讲当前已经达成了什么，以及线上部署现状

## 一句话介绍

TrumanWorld 是一个面向“可观察、可干预、可复盘”的多智能体社会模拟系统，它把 AI Agent 从单次聊天推进到一个持续运行的虚拟世界中，让多个智能体在共享环境里基于记忆、关系、状态和规则持续产生行为。

## 30 秒版本

TrumanWorld 是一个多智能体社会模拟系统。它不是简单让几个 AI 角色轮流聊天，而是构建了一个持续运行的虚拟小镇：每个智能体都有自己的状态、记忆、关系和目标，系统会按时间推进世界，让他们自然产生行为、互动和事件。

我实现了一个 tick-driven 的世界运行机制，智能体先生成行为意图，再由规则系统校验是否符合世界约束，最后落地为事件、记忆、关系变化和状态更新。用户可以通过导演控制台观察世界、查看时间线、追踪角色变化，并在必要时对世界进行干预。

项目已经完成本地运行、前后端联调和 Railway 部署验证，并且有线上链接可以访问。线上环境采用 serverless 风格的按需启动方式，所以首次打开或长时间无人访问后再次打开时，会有一段冷启动等待时间。由于多智能体持续模拟会带来较高的 token 和云服务消耗，当前不会让服务长期保持热运行。

## 2 分钟版本

TrumanWorld 的出发点是：现在很多 AI Agent 产品仍然停留在“问答”或“角色聊天”的层面，但真正有价值的 Agent 系统应该能在一个持续变化的环境中长期运行，拥有记忆、关系、状态和行为后果。

所以我做了 TrumanWorld。它是一个多智能体社会模拟系统，灵感来自《楚门的世界》和 Generative Agents。用户不是直接操控某个角色，而是像导演一样观察一个虚拟小镇的运行。小镇里的 AI 居民会根据自己的状态、记忆、关系和环境上下文做出行为，系统会记录事件、更新世界状态，并允许用户回看整个演化过程。

技术实现上，后端使用 FastAPI 承载 API 和模拟运行时，使用 SQLAlchemy、Alembic 和 PostgreSQL 管理持久化数据；前端使用 Next.js、React 和 TypeScript 构建导演控制台，并结合 2D 世界视图展示角色位置、事件和状态变化。Agent 推理层使用可替换的 Agent backend：当前主路径是 Claude Agent SDK，也支持 LangGraph backend 和 heuristic backend。这样既能用 Claude Agent SDK 承担高质量角色决策，也能通过 LangGraph 把后续更复杂的认知流程组织成图状态机，并在成本敏感场景下切换到启发式后端。

架构上，我没有把它做成简单的聊天流，而是设计成 tick-driven 的模拟架构。每一轮 tick 中，系统会读取当前世界状态、地点信息、角色状态和相关记忆，然后让智能体生成下一步行为意图。这个意图不会直接修改世界，而是先进入规则校验层。规则系统会判断这个行为是否符合地点、资源、关系和状态约束。通过校验之后，行为才会被执行，并进一步转化成事件记录、记忆变化、关系变化和世界状态变化。

这样做的好处是把“AI 的创造性”和“系统的一致性”分开：AI 负责生成有弹性的行为，规则系统负责维持世界边界和因果一致性。最终系统既能产生涌现行为，又不会完全失控。

目前项目已经完成创建世界、启动模拟、持续 tick、智能体互动、事件时间线、角色详情、世界快照和导演干预的核心闭环。前端提供了导演控制台，可以查看世界视图、事件回放、Agent 详情和干预入口。项目也已经部署到 Railway，并提供可访问的线上演示链接。线上环境采用 serverless 风格的按需启动方式，所以首次访问时可能需要等待服务冷启动；同时因为多智能体模拟会持续消耗模型 token 和云资源，当前不会让服务长期保持热运行。

## 项目要解决的问题

### 1. Agent 不应该只停留在单轮问答

很多 Agent 应用本质上仍然是“用户提问，模型回答”。这种形式很难表现长期行为、社会关系、记忆积累和环境反馈。

TrumanWorld 试图回答的问题是：如果多个 Agent 共享同一个世界，并且他们的行为会改变后续环境，会发生什么？

### 2. 多智能体系统需要可观察和可复盘

多 Agent 系统最难的问题之一不是“能不能生成内容”，而是“生成之后能不能解释”。如果一个角色突然做出某个行为，系统需要能追溯：

- 它当时在哪里
- 它看到了什么
- 它拥有哪些记忆
- 它和其他角色是什么关系
- 这个行为造成了什么后果

所以 TrumanWorld 从一开始就把事件、时间线、角色状态和世界快照作为核心能力，而不是附属功能。

### 3. AI 生成需要世界规则约束

如果完全依赖大模型自由生成，角色行为容易出现不一致，例如角色瞬移、无视地点容量、关系变化没有原因、事件无法复盘。

TrumanWorld 的方案是让 Agent 只生成行为意图，真正改变世界的动作必须经过规则系统。这使系统可以在保留创造性的同时维持世界一致性。

## 实现方案

### 1. Tick-driven 世界运行机制

系统以 tick 为单位推进模拟时间。每一轮 tick 大致分为四步：

1. 读取当前世界状态、地点状态、角色状态和相关上下文
2. 调用 Agent backend 生成角色的行为意图
3. 通过规则系统校验行为是否符合世界约束
4. 将合法行为落地为事件、记忆、关系和状态变化

这种结构让系统从“聊天程序”变成了“模拟程序”。时间推进、状态变化、事件记录和角色行为都被放进统一的运行循环里。

### 2. Agent backend 可替换

项目没有把某一个模型供应商写死在业务逻辑中，而是抽象出 Agent backend。当前代码里有三类后端：`claude_sdk`、`langgraph` 和 `heuristic`。默认主路径使用 Claude Agent SDK，LangGraph backend 用于把后续更复杂的认知流程组织成可控的图状态机，heuristic backend 则用于低成本运行和链路验证。

这个设计很重要，因为多智能体模拟的成本压力比普通聊天应用更明显。一次模拟中可能有多个角色、多轮上下文、多次决策，如果推理层不能替换，系统后续很难优化成本和性能。把 Claude Agent SDK、LangGraph 和 heuristic 都收敛到同一层 backend 接口后，模拟核心不需要关心具体推理实现。

### 3. 行为意图与规则执行分离

智能体生成的是 action intent，也就是“想做什么”。但这个意图是否真的发生，要由规则系统判断。

例如，一个角色想去某个地点、和某个人互动、触发某个事件，系统会检查地点、角色状态、关系、资源和世界约束。只有通过校验，行为才会被执行。

这种设计让 AI 不直接拥有“改写世界”的权限。它可以提出行为，但世界是否接受这个行为，由系统规则决定。

### 4. 事件时间线与世界快照

所有关键行为都会被记录为事件。事件不只是日志，而是复盘世界演化的基础数据。

前端可以基于事件时间线查看：

- 某个角色做了什么
- 某个地点发生了什么
- 某个 tick 中世界如何变化
- 某个干预对后续行为产生了什么影响

世界快照则用于展示当前状态，让用户可以从宏观层面理解小镇正在发生什么。

### 5. 导演控制台

前端不是传统后台管理界面，而是一个导演控制台。它的目标不是让用户填表，而是让用户观察和干预一个持续运行的世界。

当前控制台包含：

- Run 列表：创建和管理模拟运行
- 世界视图：查看角色位置、状态和最近行为
- 时间线：回放事件流
- Agent 详情：查看角色记忆、关系和历史事件
- 导演干预：向世界注入外部事件或条件

## 已经成功达成的结果

当前项目已经不是一个单页概念 demo，而是完成了多智能体模拟的核心闭环。

已经达成的部分包括：

- 可以创建一个模拟世界
- 可以启动、暂停和继续模拟运行
- 系统可以按 tick 持续推进世界时间
- 多个智能体可以基于上下文生成行为
- 行为会经过规则系统校验
- 合法行为会转化成事件、记忆、关系和状态变化
- 前端可以展示世界视图、事件时间线和 Agent 详情
- 用户可以通过导演控制台观察和干预世界
- 项目已经完成 Railway 部署链路验证，并提供可访问的线上演示链接

这意味着 TrumanWorld 已经具备了一个多智能体社会模拟平台的基本形态：有世界、有角色、有时间、有事件、有规则、有观察界面，也有外部干预入口。

## 部署现状

项目已经部署到 Railway，并验证了线上部署链路。当前有可访问的线上演示链接，但采用 serverless 风格的按需启动方式。

不过，多智能体模拟和普通 Web 应用不一样。它的运行成本主要来自两个方面：

- 多个 Agent 在持续 tick 中反复进行上下文推理，会产生较高 token 消耗
- 世界持续运行需要后端服务和数据库资源，云服务也会产生额外成本
- serverless 按需启动可以降低空闲成本，但首次访问或长时间空闲后再次访问会出现冷启动等待

因此当前线上版本可以通过链接访问，但不会长期保持热运行。更准确的表述是：

> 系统已经具备线上运行能力，并完成 Railway 部署验证。当前有线上演示链接可以访问，但服务采用 serverless 风格的按需启动方式，所以首次访问时可能需要等待冷启动。由于多智能体持续模拟会带来较高的 token 与云服务消耗，当前不会让服务长期保持热运行。

这不是功能没有完成，而是成本控制策略。下一阶段会围绕低成本运行继续优化，例如：

- 降低单轮 tick 的上下文长度
- 增加模型调用缓存
- 对不同类型决策使用不同强度的模型
- 支持本地模型或更轻量的推理后端
- 减少不必要的后台持续推理

## 比赛答辩推荐结构

### 开场

我做的是 TrumanWorld，一个多智能体社会模拟系统。它的目标不是做一个更会聊天的角色，而是让多个 AI 角色在同一个持续运行的世界里生活、互动、留下记忆，并被用户观察和干预。

### 问题

目前很多 Agent 项目仍然停留在单次对话或固定工作流中，很难表现长期行为、社会关系和环境反馈。而多 Agent 系统真正有意思的地方，恰恰在于多个角色长期共处后产生的涌现行为。

### 方案

我的方案是构建一个 tick-driven 的虚拟世界。每一轮 tick 中，系统读取世界状态和角色上下文，让 Agent 生成行为意图，再通过规则系统校验，最后把行为落地为事件、记忆、关系和状态变化。

技术上，后端使用 FastAPI、SQLAlchemy、Alembic 和 PostgreSQL，前端使用 Next.js、React 和 TypeScript。Agent backend 当前主路径是 Claude Agent SDK，同时支持 LangGraph 和 heuristic 后端，因此后续可以在高质量推理、图状态机编排和低成本演示之间切换。

### 结果

目前系统已经跑通从创建世界、启动模拟、持续推进、智能体互动、事件回放、角色详情到导演干预的完整闭环。项目也已经部署到 Railway，验证了线上运行能力，并且有线上链接可以访问。由于持续模拟会消耗较多 token 和云资源，线上环境采用 serverless 风格的按需启动方式，首次访问可能需要等待冷启动。

### 价值

这个项目的价值在于，它把 Agent 从“回答问题”推进到“在世界中持续行动”。它可以用于游戏 NPC、剧情生成、社会仿真、Agent 行为研究，以及多智能体系统的可视化评估。

## 面试问答备选

### Q: 这个项目和普通 AI 角色聊天有什么区别？

普通角色聊天主要是对话上下文驱动，角色说完一句话后，很少有真实的世界状态变化。TrumanWorld 里，角色行为会进入世界运行循环，影响事件、记忆、关系和后续状态。也就是说，它不是只有“对话”，而是有“行为后果”。

### Q: 为什么要设计规则系统？

因为完全让大模型决定世界变化会不稳定。模型可以生成有创意的行为，但它不适合直接维护世界一致性。规则系统相当于世界的边界，负责判断行为是否合理，以及行为会造成什么后果。

### Q: 为什么线上链接打开需要等待？

项目已经部署到 Railway，并有可以访问的线上演示链接。但线上环境采用 serverless 风格的按需启动方式，如果服务长时间没有访问，再次打开时需要先启动前后端服务，所以会有一段冷启动等待。这样做主要是为了控制云服务成本。

### Q: 为什么不让线上服务一直热运行？

多智能体模拟会持续调用模型服务，一次运行可能包含多个角色、多轮上下文和多次决策，所以 token 和云服务消耗都比较高。如果让服务长期热运行，成本会明显上升。当前策略是保留可访问链接和完整部署链路，但按需启动演示。

### Q: 如果继续做，下一步会优化什么？

下一步会重点优化三件事：第一是降低推理成本，例如上下文压缩、缓存和分层模型；第二是增强角色心智模型，让角色拥有更稳定的目标、情绪和长期记忆；第三是完善导演工具，让用户能更清晰地观察因果链路和干预效果。

### Q: 项目的最大难点是什么？

最大难点不是让模型生成一句合理的话，而是让多个 Agent 在长期运行中保持一致性。角色要记得过去，行为要符合当前世界，事件要能影响后续状态，用户还要能回看和理解这些变化。所以架构重点放在世界循环、规则约束、事件记录和状态更新上。
