# 3D Stage V2：可观察的微缩小镇

## 1. 决策

Truman World 的主舞台采用「安静、可观察的低多边形微缩小镇」方向。前端继续使用
React Three Fiber / Three.js，与现有 Next.js 导演台、实时数据流和无障碍 DOM 交互保持同构；
本阶段不引入 Godot 作为主客户端。

V2 不是继续提高 voxel 方块密度，而是把现有程序化场景作为可靠 fallback，逐步替换为
Blender 制作、glTF/GLB 交付的低多边形资产。行为状态、连续路径移动和事件气泡仍由现有
仿真协议驱动。

## 2. 已批准视觉基线

- [Golden Frame](../images/3d-v2-golden-frame.webp)：世界占据主要视野，右侧信息只在需要时出现。
- [材质与色彩板](../images/3d-v2-palette.webp)：苔绿、砖红、石灰白、板岩蓝和窗灯琥珀色。

参考权重：Tiny Glade 的材质与生活细节、Townscaper 的整体构图、Smallville 的行为可读性。
不复制任何单一产品的界面或资产，也不采用游戏 HUD、霓虹科幻和高饱和 Minecraft 语汇。

## 3. Golden Slice 范围

第一个可验收切片只做一个完整街区，不做一座半完成的大城：

- 核心地点：街角咖啡馆、两组住宅、口袋公园。
- 地标：市政钟、老橡树。
- 居民：6 人，至少覆盖行走、交谈、阅读、工作、休息五种可辨动作。
- 街道细节：弯曲铺装路、长椅、路灯、自行车、店招、花盆和窗灯。
- 时间：黎明、上午、正午、下午、黄昏、夜间六个连续视觉状态。
- 信息结构：世界默认全宽；点选地点后展开窄信息抽屉；深度详情仍使用模态页。

Golden Slice 完成后再将资产语言扩展到医院、图书馆、办公室和大型广场。

## 5. 资产管线

运行时注册表位于 `frontend/components/voxel/asset-registry.ts`。每项资产必须具备：稳定 ID、
GLB URI、类型、变体、三角面预算和程序化 fallback。只有状态为 `ready` 的资产才能触发加载，
防止尚未交付的路径产生 404。

### 5.1 Blender 导出约定

- 单位 1 m，Y up；模型原点位于地面中心或入口锚点。
- 应用 transform，正面朝 +Z；命名使用 `kind.name.variant`。
- 合并静态网格，复用材质；颜色贴图使用 sRGB，其余数据贴图使用 Linear。
- 使用 glTF 2.0 `.glb`；优先 KTX2 纹理与 Draco/Meshopt 压缩。
- LOD0 用于近景，复杂资产预留 LOD1；不把灯光、相机和无关动画导出。
- 当前开发机未安装 Blender；模型生产开始前需提供 Blender 4.x 和确定性的导出脚本。

## 6. 技术架构

```text
WorldSnapshot
  -> SceneWorld（时间、地点、居民、路径、事件）
  -> ScenePlan（布局和 fallback prefab）
  -> Asset Registry（ready GLB 或 fallback）
  -> R3F Renderer（PBR、AgX、雾、阴影、实例化）
  -> DOM Overlay（抽屉、事件、可访问控制）
```

Godot 保留为未来独立沉浸式客户端的研究路线，详见
[Godot 3D Client Spike](../engineering/GODOT_3D_CLIENT_SPIKE.md)。它不应阻塞网页 Golden Slice。

## 7. 验收标准

### 视觉与体验

- 1440×900 首屏中，世界画面占可用内容区至少 80%。
- 不操作时不显示常驻右栏；地点选择反馈在 250 ms 内出现。
- 六个时段在不依赖文字标签时仍能被区分，夜间关键人物和路径保持可读。
- 咖啡馆、住宅和公园仅靠轮廓与材质即可区分；不是靠浮动标签补救。
- 居民行为至少能通过姿态、位置或道具中的两项识别。

### 性能与可靠性

- 桌面 Golden Slice 目标不超过 35 draw calls；现有 fallback 基线约 22。
- 首屏 GLB 压缩总量不超过 8 MB，单张纹理不超过 2048 px。
- 典型 6 居民场景在中端集显保持 50 FPS 以上，交互时不得持续重绘静止帧。
- WebGL 或单个资产加载失败时回退到程序化场景，导演功能仍可操作。
- `prefers-reduced-motion` 下关闭非必要环境动画，连续移动仍提供终点状态。

## 8. 交付门槛

1. 先完成咖啡馆街区的真实资产与昼夜对照截图。
2. 通过视觉审查、键盘操作、前端测试和性能预算后，才扩展第二街区。
3. 每个新增地点必须同时交付模型、碰撞/选择锚点、夜间表现和 fallback 映射。
4. 不接受以更多面板、标签或 bloom 掩盖模型轮廓与构图问题。

## 9. 当前实现状态

在真实 GLB 资产交付前，程序化 fallback 已升级为可实例化的低多边形几何系统：

- `box`、八边圆柱、四面锥体和一级细分二十面体共享几何资源。
- 住宅、咖啡馆和图书馆使用四坡屋顶，不再用三层方块模拟屋顶。
- 树木、喷泉、路灯、户外桌和街具具备不同轮廓；建筑窗户使用独立琥珀发光层，并随清晨、白昼、黄昏与夜间光照档位分级改变强度。
- 地台根据地点和道路范围自动收紧，边缘树群承担画面构图，不再铺设棋盘草坪。
- Scene Plan 已拆分核心交互层与外围氛围层：真实地点保持稳定点击语义，外围建筑、树带和道路出口
  只承担世界规模感，不伪装为可交互地点。
- 默认镜头使用独立的 `focusBounds` 框定核心街区，完整 `bounds` 保留外围可探索范围；扩展世界时
  不会因为自动 fit 而把居民和核心建筑继续缩小。
- `seaside` / `boardwalk` 主题会生成海面、海堤和码头，`campus` 主题会生成外围教学建筑与纵深步道；
  所有氛围几何继续复用实例化材质批次，不增加模型下载。
- 普通不透明颜色通过 `instanceColor` 合并进共享 matte 材质；玻璃、水面和自发光材质单独分层，避免为每个色板 token 增加 draw call。
- 当前 Neon smoke test 浏览器实测为 22 draw calls、约 21.1k triangles、17 geometries；分层地形、街区绿化、四类建筑的独立窗户发光层、五个 ready 资产与 12 边道路均启用后仍显著低于 35 draw calls 预算。
- 居民由收腰六面躯干、低面数头部、六边形肢体和方形道具四类共享几何构成；衣袖、前臂、裤装和鞋分色，同类部件跨居民实例化绘制。
- 居民状态通过轮廓表达：移动时反向摆臂、交谈时抬臂、工作时持有道具、休息时坐姿阅读；胸前小徽记颜色只作辅助。
- 道路按导航边生成连续连接段，并用圆角节点覆盖端点、转角、交叉口和广场；路缘、路面、地块和建筑基座使用统一薄层比例，不再逐格堆叠厚铺面。
- 居民入口锚点采用错落马蹄形编队；静止居民朝向建筑，交谈居民朝向小组中心，避免多人横向排成一列。
- 场景比例常量统一约束门高、建筑基座、道路和居民落地高度；正式 Blender 资产应继续沿用这套显示单位。
- 空间基础采用“多层街区围合”方向：喷泉广场保持第一视觉中心，老橡树作为安静副中心；外围使用 0.07–0.14 显示单位的低频绿地台地、树丛和石块收边，核心导航面继续保持平整。
- 每个非广场地点拥有道路至入口的连续门前路径；住宅用低矮树篱形成私密边界，商业和公共服务建筑通过成对花池建立可识别的前场。
- 居民移动使用按弧长采样的连续世界坐标；道路折角通过小半径二次曲线平滑。前端 locomotion 由速度、加速度和剩余制动距离驱动，不再按固定时长插值；居民拥有稳定的个体步速，步态相位绑定真实行进距离，朝向提前观察弯道，并在抵达后自然转向活动目标。后端进度只用于温和追赶，不直接造成画面跳点。
- 地点规划为交谈、工作和休息生成稳定语义槽位：交谈者围向小组中心，工作者靠近建筑入口，休息者分布在前场两侧；移动与空闲共用到达槽位，避免后端确认抵达时发生位置跳变。
- 活动槽位与克制的街区设施共用同一空间基准：公园和市政区提供朝向内侧的长椅，商业区保留单一共享桌，住宅以邮箱提示日常活动，公共服务入口使用低矮工作台；设施按街区分化而非逐槽位复制，保持世界可读且不过度装饰。
- 默认镜头按每个真实场景块的旋转包围盒投影计算正交 fit，不再用最高点与最远边角拼成的全局空盒预留空间；桌面使用低角度导演视角，竖屏自动提高俯视角，使小镇在不同画布比例下都充分占据可用区域，同时避开顶部与底部控件。
- 行人 steering 在权威道路中心线上叠加相对行进方向的稳定右侧偏移，对向居民因此自然分流；同起点、同终点、同路线的居民按双人一排形成同行编队，后续行保持 0.42 显示单位的跟随距离并共享步速。运行时局部排斥限制在 0.1 显示单位内；队伍纵向间距先于车道侧偏消退，使同行者在目的地前自然解散并收束到真实入口锚点。
- 三向及四向道路节点会生成稳定路口检查点。同一编队共享通行权；已进入路口的居民优先完成穿越，否则按稳定编队 ID 决定先后，需要让行者在接近路口时渐进减速。该规则只使用权威道路拓扑，不依赖随机帧序，因此不会因刷新顺序抖动或互相等待形成死锁。
- 关系亲疏目前只由居民详情接口返回，世界快照尚未提供全体关系图；在协议补齐前，同行编队只根据同起点、同终点、同路线的事实形成，不把“同路”伪装成朋友关系。后续关系感知的结伴行为必须先扩展快照协议并明确隐私与性能边界。

这些 fallback 组件用于验证构图、比例、选择锚点和昼夜材质。它们不是首批 GLB 资产的替代品。

首批五个真实资产已进入 `ready` 状态：

- `frontend/public/world/buildings/cafe-corner.glb`，约 59 KB；
  `frontend/public/world/buildings/home-row.glb`，约 41 KB；
  `frontend/public/world/buildings/office-midrise.glb`，约 73 KB；
  `frontend/public/world/buildings/clinic-corner.glb`，约 45 KB；
  `frontend/public/world/vegetation/old-oak.glb`，约 79 KB。五者均为 glTF 2.0 二进制。
- 通过 `pnpm assets:world` 确定性生成，色板、轴向、单位和 mesh 合并策略固化在脚本中。
- 咖啡馆、联排住宅、办公楼和诊所各自合并为一个顶点色 PBR 外壳 mesh 与一个独立窗户发光 mesh，老橡树公园保持单 mesh；同一资产的多个 placement 共享一次加载，并通过 `InstancedMesh` 批量绘制。
- 建筑生成器复用门框、窗框、窗台、台阶和入口雨棚模块；办公楼通过层高与窗格节奏建立竖向轮廓，诊所通过矮体量、十字标识和入口雨棚建立公共服务辨识度。
- ScenePlan 根据 `locationType` 或视觉 preset 选择 ready 资产，并按建筑 footprint 或公园 plot 尺寸缩放；商店、商场等未匹配地点保留各自 prefab，避免重复建筑。
- 加载期间或加载失败时渲染同地点的程序化 fallback；加载成功后保留地点点击和镜头锚点。
